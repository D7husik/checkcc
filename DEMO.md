# CI/CD: демо и следующие шаги

## Что сделано

Настроен полный путь кода от ветки до прода на своих GitHub Actions runner'ах. Прод работает без Docker, как у заказчика.

```
ветка ─PR─► CI ─merge─► test ─► деплой на стенд (Docker)
                         └─PR─► main ─► «готов к деплою» ─кнопка─► прод (systemd)
```

| Этап | Что происходит | Что это даёт |
|---|---|---|
| CI | ruff, тесты на настоящей MySQL, проверка миграций, сборка образа | ошибка видна в PR, до ревью |
| Стенд | автодеплой при merge в `test`: бэкап, миграции, проверка `/health/ready`, автооткат | изменения видно без ручной выкладки |
| Прод | кнопка Run workflow: релиз в отдельной папке, бэкап, миграции, переключение, проверка, автооткат | заказчик сам решает, когда выкатывать, остальное автоматически |
| Защита | на прод попадает только то, что прошло стенд | нельзя выкатить непроверенный код |
| Кнопки Ops | статус, бэкап, откат | не нужен доступ на сервер |

Схема полностью отлажена здесь, в тестовом репозитории `checkcc`. После согласования переносится в CRM (что меняется, описано в [docs/CI_CD.md](docs/CI_CD.md) §9).

## Сценарий показа (~15 минут)

### Шаг 1. Runner'ы
Settings → Actions → Runners: три runner'а (`ci`, `test-env`, `prod-env`) в статусе Idle.

### Шаг 2. CI ловит ошибку
```bash
git checkout -b demo-lint origin/test
# добавить в app/main.py строку: import os
git commit -am "demo: unused import"
git push -u origin demo-lint
```
Открыть PR `demo-lint → test`. Ожидаемо: ❌ `lint`, остальные job'ы отработали независимо. В логе job'а строка `Runner name` показывает, что он шёл на нашем runner'е. Удалить строку, запушить: всё зелёное.

### Шаг 3. Стенд обновляется сам
Смержить PR в `test`. Ожидаемо: workflow `deploy-test` зелёный, `curl localhost:8001/health/ready` → `"status":"ok"`, на коммите статус `deploy/test`.

### Шаг 4. Прод только по кнопке
Открыть PR `test → main`, смержить методом **Create a merge commit**. Ожидаемо: workflow `Deploy prod` зелёный, job `deploy` пропущен, в Summary написано «готов к деплою». Прод не менялся.

**Actions → Deploy prod → Run workflow** (ветка `main`). Ожидаемо:
- `curl localhost:8002/health/ready` → `"status":"ok"`;
- `readlink ~/checkcc-prod/current` показывает новый релиз;
- в `~/checkcc-prod/backups/prod/` появился новый дамп.

### Шаг 5. Обойти стенд нельзя
Закоммитить что-нибудь прямо в `main` и запустить Run workflow. Ожидаемо: ❌ `check` («is not a merge»), деплоя нет.

### Шаг 6. Откат кнопкой
**Actions → Ops → Run workflow**: `prod`, `rollback`. Ожидаемо: `current` указывает на предыдущий релиз, сервис отвечает. Если после отката схема новее кода, статус будет `degraded`.

## Статус

| Требование | Статус |
|---|---|
| Изменения автоматически проверяются в каждом PR | ✅ |
| Стенд обновляется при merge в `test` | ✅ |
| Деплой на прод с бэкапом, миграциями и автооткатом | ✅ в тестовом репозитории |
| На прод попадает только прошедшее стенд | ✅ |
| Перенос в CRM | ⏸ следующий этап |

## Что нужно для переноса в CRM

1. **От владельца репозитория:** токены регистрации runner'ов, ветка `test`, настройка метода merge.
2. **От заказчика:**
   - согласие поставить на машину runner и пользователя `deployer`;
   - версия Ubuntu, имя текущего сервиса, путь к коду, расположение `.lab_env`;
   - есть ли у машины доступ к github.com;
   - права пользователя БД на `mysqldump` и изменение схемы;
   - тихое окно для первого переключения.
3. **От команды:** Telegram-бот и `chat_id`, синхронизация ветки CI/CD с `main`.
