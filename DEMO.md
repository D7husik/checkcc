# CI для FastAPI: демо и следующие шаги

## Что сделано

Настроен CI-пайплайн на GitHub Actions. Каждое изменение кода проверяется автоматически, до мержа в `main`.

```
PR / push в main
      │
      ▼
┌──────────────┐     ┌──────────────────────────────┐
│     lint     │ ──▶ │  docker build & smoke check  │
└──────────────┘     └──────────────────────────────┘
 ruff check            сборка Docker-образа
 ruff format --check   запуск контейнера + GET /health
```

| Проверка | Что ловит |
|---|---|
| `ruff check` | Ошибки в коде: неиспользуемые импорты, импорт не в начале файла, потенциальные баги |
| `ruff format --check` | Нарушение единого стиля: пробелы, кавычки, пустые строки |
| Docker build | Образ не собирается (зависимости, Dockerfile) |
| Smoke check `/health` | Приложение собралось, но не запускается или не отвечает |

Если `lint` упал, `docker` не запускается: сначала идёт быстрая проверка, дорогая только после неё.

---

## Перед показом

- [ ] Последний запуск CI на `main` зелёный: **Actions → CI**.
- [ ] Включена защита ветки: **Settings → Branches** → правило для `main` → **Require status checks to pass** → `Lint (ruff)` и `Docker build & smoke check`.
- [ ] Локально стоит свежий `main`: `git checkout main && git pull`.
- [ ] Открыты вкладки: репозиторий, **Actions**, файл `.github/workflows/ci.yml`.

## Сценарий показа (~10–15 минут)

### Шаг 1. Устройство пайплайна
Открыть `.github/workflows/ci.yml` и показать:
- **когда запускается:** любой pull request, push в `main`, ручной запуск;
- **job `lint`:** `ruff check` и `ruff format --check`;
- **job `docker`:** сборка образа и проверка `/health`, стартует только после успешного `lint`.

### Шаг 2. Зелёный пайплайн
**Actions** → последний запуск на `main` → оба job'а ✅.
Открыть `Docker build & smoke check` → шаг **Smoke check /health**: в логе `{"status":"ok"}` и `App is healthy`.

### Шаг 3. Ошибка в коде
```bash
git checkout -b demo-lint
# добавить в начало app/main.py строку: import os
git commit -am "demo: unused import"
git push -u origin demo-lint
```
Открыть pull request `demo-lint → main`.

**Ожидаемый результат:**
- ❌ `Lint (ruff)`: в логе `F401 'os' imported but unused`;
- ⏭ `Docker build & smoke check`: Skipped, сборка не запускалась;
- кнопка **Merge** заблокирована;
- на вкладке **Files changed** ошибка подсвечена на строке.

### Шаг 4. Ошибка стиля
В том же PR удалить `import os`, а в `app/main.py` в функции `health` убрать пробел: `{"status":"ok"}`.
```bash
git commit -am "demo: style issue"
git push
```
**Ожидаемый результат:**
- ✅ шаг `Ruff check`: ошибок в коде нет;
- ❌ шаг `Ruff format`: в логе diff `{"status":"ok"}` → `{"status": "ok"}`.

Исправление одной командой:
```bash
.venv/bin/ruff format .
git commit -am "style: ruff format"
git push
```
Оба job'а ✅, кнопка **Merge** разблокирована. После этого PR можно закрыть: изменений относительно `main` в нём не осталось.

### Шаг 5 (дополнительно). Код в порядке, но приложение не запускается
```bash
git checkout main && git checkout -b demo-docker
# в Dockerfile заменить app.main:app на app.main:wrong
git commit -am "demo: broken startup"
git push -u origin demo-docker
```
Открыть PR.

**Ожидаемый результат:**
- ✅ `Lint (ruff)`;
- ❌ `Docker build & smoke check`: шаг **Smoke check /health** падает через 30 секунд;
- в шаге **Container logs (on failure)** видна причина:
  `Error loading ASGI app. Attribute "wrong" not found in module "app.main".`

После показа PR закрыть без мержа.

## Статус задачи

| Требование | Статус |
|---|---|
| Изменения автоматически проверяются в каждом PR | ✅ lint, стиль, сборка, smoke check |
| Код с ошибками не попадает в `main` | ✅ при включённой защите ветки |
| Тесты (pytest) | ⏸ не входили в текущий объём. Smoke check проверяет только запуск, а не логику |
| Изменения из ветки автоматически уходят на деплой (CD) | ⏸ нужна информация о текущем процессе деплоя |
| CI на основном проекте | ⏸ после согласования. Перенос описан в `README.md` |

## Возможные следующие шаги

**Вариант 1. Оставить только CI.**
`main` защищён проверками, а деплой выполняется как сейчас. Остаётся перенести пайплайн на основной проект.

**Вариант 2. CI + готовый к деплою образ (Continuous Delivery).**
После мержа в `main` Docker-образ автоматически публикуется в registry (GitHub Container Registry) с тегами `latest` и `sha-<коммит>`. Этот шаг подходит для любого способа деплоя и не требует доступа к серверу. Его можно сделать сразу.

**Вариант 3. Полный CD (автодеплой).**
После мержа новая версия сама выкатывается на сервер. Способ зависит от инфраструктуры:

| Как деплоится сейчас | Что добавляется в пайплайн |
|---|---|
| Вручную по SSH (`git pull`, перезапуск) | Job, который выполняет эти же команды по SSH |
| Docker compose на сервере | Публикация образа + обновление на сервере (SSH или Watchtower) |
| Kubernetes | Публикация образа + ArgoCD/Flux или `kubectl` |
| Облачная платформа (PaaS) | Автодеплой из ветки `main` в настройках платформы |
| Деплой на стороне клиента | Публикация образа + вебхук в пайплайн клиента |

Дополнительно можно добавить **тесты (pytest)** отдельным job'ом между `lint` и `docker`.

## Вопросы для обсуждения

1. **Какой объём задачи?** Только CI или CI вместе с автодеплоем?
2. **Как сейчас деплоится проект?** Кто это делает и какими действиями: команды, кнопка, скрипт?
3. **Куда деплоим?** Наш сервер, Kubernetes, облачная платформа или сервер клиента?
4. **Что деплоим?** Docker-образ или код из git?
5. **Из какой ветки идёт деплой?** `main` или отдельная (`release`, `prod`)? Есть ли тестовый стенд (staging)?
6. **Когда выкатывать?** Автоматически после мержа или по кнопке с ручным подтверждением?
7. **Какие доступы нужны и кто их выдаёт?** SSH-ключ, токен registry, вебхук клиента.
8. **Когда добавлять тесты** и какие сценарии покрыть в первую очередь?
